Yes. For your purpose, two ESP32s can be turned into a surprisingly capable 2.4 GHz antenna/link characterization system, especially if the goal is comparing antennas, detecting bad matching, measuring relative gain versus direction, or finding frequency/channel dependence.

The key is to use the ESP-IDF Wi-Fi driver from Arduino rather than the high-level WiFi.h API.

What you can measure

Measurement	ESP32 capability	Usefulness for antenna testing

RSSI of received packets	Excellent	★★★★☆
Packet error / CRC failure rate	Excellent with promiscuous mode	★★★★☆
PHY parameters	Excellent	★★★★☆
Noise-floor estimate	Available on several ESP32 variants	★★★★☆
Channel number / bandwidth	Yes	★★★★★
CSI — complex channel response per subcarrier	Yes	★★★★★
Frequency response across 20 MHz	Yes, indirectly through CSI	★★★★★
Absolute RF power measurement	Poorly calibrated	★★☆☆☆
Continuous spectrum analyzer	No, not really	★★☆☆☆
Antenna radiation pattern	Yes, using two nodes	★★★★★
VSWR / S11	No	☆☆☆☆☆


Espressif exposes esp_wifi_set_csi_rx_cb(), esp_wifi_set_csi_config() and esp_wifi_set_csi() for Channel State Information. The CSI record contains the received PHY metadata plus complex I/Q values for the individual OFDM subcarriers. 

This is the interesting part: on 802.11n 20-MHz operation, CSI can contain 56 subcarrier measurements, and for 40 MHz up to 114, with each measurement carrying imaginary and real components. 

So instead of merely getting:

RSSI = -61 dBm

you can obtain something conceptually like:

subcarrier       Re       Im       magnitude      phase
---------------------------------------------------------
-28              ...
-27              ...
...
+27              ...
+28              ...

That is much closer to an RF frequency-response measurement.

The architecture I would use

I would build the system as:

RF path
        ┌────────────────────────┐
        │                        │
        ▼                        ▼
   ESP32 TRANSMITTER  ~~~~~>  ESP32 RECEIVER
      controlled TX              CSI/RSSI
        │                           │

The transmitter would not necessarily need to be a conventional AP.

The ESP-IDF driver allows raw 802.11 transmission through esp_wifi_80211_tx(), including beacon, probe, action and non-QoS data frames. Espressif also provides a function for configuring the 802.11 TX rate. 

That gives you an important advantage: you can make the transmitter generate a very controlled, repeatable signal.

Then:

same conditions

The receiver records the entire result.

1. RSSI is already surprisingly useful

In promiscuous mode:

esp_wifi_set_promiscuous(true);
esp_wifi_set_promiscuous_rx_cb(rxCallback);

the callback receives wifi_promiscuous_pkt_t, whose rx_ctrl contains radio metadata.

Depending on the ESP32 generation, this includes fields such as:

rssi
channel
timestamp
sig_len
rx_state
antenna
noise_floor

For example, Espressif documents the RX metadata structure including RSSI and RF noise-floor information on supported variants. 

You could therefore collect:

timestamp
channel
RSSI
noise floor
packet length
PHY mode
MCS
antenna index
CRC/rx state

for every packet.

For antenna A versus antenna B, relative RSSI measurements can be very good, provided you control geometry and keep the RF environment fixed.

2. CSI is where this becomes really interesting

CSI gives you substantially more information.

Think of the received signal as

\[
Y(f)=H(f)X(f)
\]

where:

\(X(f)\) = transmitted signal

\(H(f)\) = propagation + antenna + RF-chain response

\(Y(f)\) = received signal


CSI gives you an estimate of \(H(f)\).

In practice:

antenna
             +
             |
             v
        RF propagation
             |
             v
       ESP32 receiver
             |
             v
       CSI subcarriers
             |
             v

   H(-28) ... H(-1) H(0) H(+1) ... H(+28)

The magnitude could be plotted:

dB
 ^
 |       /\         ______
 |      /  \_______/      \____
 |_____/__________________________> frequency
       -10   -5   0   +5   +10 MHz

This can reveal:

antenna resonance effects

frequency-dependent gain

mismatch-related response

multipath

polarization changes

small mechanical changes

cable/connector problems

enclosure effects


Espressif explicitly documents the CSI data as complex imaginary/real values for each subcarrier and notes that RSSI, RF noise floor, reception time and antenna information are available alongside CSI in rx_ctrl.

3. Important limitation: CSI is NOT a spectrum analyzer

This distinction is crucial.

The ESP32 cannot simply do:

measure RF energy every 100 kHz

across the whole 2.4-GHz band like a laboratory spectrum analyzer.

CSI is derived from received 802.11 packets.

Therefore your frequency-domain information is approximately:

20 MHz Wi-Fi channel
┌─────────────────────────────────┐
│ • • • • • • • • • • • • • • • │
└─────────────────────────────────┘
       CSI subcarriers

rather than:

2400 MHz ───────────────────────── 2500 MHz
             continuous spectrum

However, you can overcome much of this by stepping through Wi-Fi channels.

For example:

CH1   2401–2423 MHz
CH2   2406–2428
CH3   2411–2433
...
CH13  2461–2483

and obtain:

channel 1  -> CSI
channel 2  -> CSI
channel 3  -> CSI
...
channel 13 -> CSI

This creates a fairly useful coarse frequency-response measurement across the Wi-Fi band.

esp_wifi_set_channel() is exposed specifically for controlling the primary/secondary channel; Espressif documents its use for this type of low-level operation, including promiscuous/sniffer use.

8. A very useful measurement is differential CSI

Rather than looking at absolute CSI:

\[
H_{test}(f)
\]

I would use a reference antenna:

\[
H_{ref}(f)
\]

and calculate

\[
G(f)=20\log_{10}
\left(
\frac{|H_{test}(f)|}{|H_{ref}(f)|}
\right)
\]

This largely cancels:

cable effects

TX power variation

receiver gain variations

propagation loss

some environmental effects


So your output becomes something like:

Test antenna relative response

 +3 dB       ______
             /      \
  0 dB _____/        \______
 -3 dB
 -6 dB
        2400       2440       2480 MHz

That's much more meaningful for antenna comparison.

9. I would also record the noise floor

On supported ESP32 variants the PHY RX metadata exposes a noise-floor measurement. 

That lets you distinguish:

RSSI = -60 dBm

from:

RSSI = -60 dBm
noise floor = -95 dBm

versus:

RSSI = -60 dBm
noise floor = -65 dBm

Those are obviously very different RF situations.

A particularly useful metric is:

\[
SNR \approx RSSI-NF
\]

which can be correlated with packet error rate.

Because antennas can behave differently in TX and RX due to the RF path, connectors, matching and ESP32 hardware, I would eventually implement:

For example:

Test 1:

Test 2:

ESP32 #1 → reference antenna
ESP32 #2 → antenna A

This lets you separate:

antenna performance

from:

11. One major warning about using two ordinary ESP32 boards

Do not assume:

RSSI = actual received power in dBm

is laboratory accurate.

The reported RSSI is a receiver estimate and the absolute calibration can vary between chips, boards, RF designs and configurations.

For antenna development, I would therefore emphasize:

relative measurements > absolute measurements

and establish a reference configuration:

reference antenna
reference distance
reference orientation
reference channel
reference TX power
reference PHY rate

Then report:

ΔRSSI
ΔCSI
ΔPER
ΔSNR

rather than pretending you're measuring absolute antenna gain to ±0.1 dB.

12. The most powerful setup I'd recommend

For your ESP32/Arduino environment, I'd implement two firmware modes.

ESP32-A — RF transmitter

- fixed MAC
- programmable channel
- programmable HT20/HT40
- programmable TX power
- programmable PHY rate
- programmable packet length
- programmable packet interval
- sequence number
- timestamp
- raw 802.11 transmission

ESP32-B — RF analyzer

promiscuous mode
      +
CSI
      +
RX metadata
      +
packet statistics

Each measurement record could be:

struct RFMeasurement {
    uint32_t timestamp_us;

    uint8_t channel;
    uint8_t bandwidth;
    int8_t rssi;
    int8_t noise_floor;

    uint16_t packet_len;
    uint8_t rate;
    uint8_t mcs;

    uint32_t sequence;
    bool crc_ok;

    uint16_t csi_len;
    // CSI data stored separately
};

The CSI callback should not perform heavy processing. Espressif explicitly warns that it runs in the Wi-Fi task, recommending that the callback put the required information into a queue and have another task process/store it. 

For your style of ESP32 firmware, I'd use a fixed-size ring buffer, not std::vector/dynamic allocation in the callback.

The important conclusion

For what you described, I would not concentrate on trying to turn the ESP32 into a conventional spectrum analyzer.

Instead, I'd build:

controlled transmitter + promiscuous receiver + CSI + channel sweep + packet statistics.

That gives you something much more useful for antenna work than a simple RSSI scanner.

The most interesting measurement would be:

\[
\boxed{
\text{channel}
\times
\text{angle}
\times
\text{CSI}(f)
\times
\text{RSSI}
\times
\text{PER}
}
\]

That could produce a genuinely useful ESP32-based antenna characterization instrument, albeit not a calibrated VNA or laboratory spectrum analyzer.

For a concrete implementation, the next step I'd recommend is building the Arduino-compatible ESP32 analyzer firmware around esp_wifi_set_promiscuous(), esp_wifi_set_csi_config(), esp_wifi_set_csi_rx_cb(), esp_wifi_set_csi(), esp_wifi_set_channel() and esp_wifi_80211_tx(), with a zero/low-heap ring buffer and a binary serial output format for Python analysis. The relevant low-level APIs are documented by Espressif.
